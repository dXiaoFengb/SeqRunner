# 需求澄清与实施计划

- 何时读取：准备首版实现或新一轮功能新增、修复、优化，需要澄清需求、编写、认可或修订实施计划时。
- 职责：多轮澄清、计划内容与保存、认可来源和范围变更；不替代立项结束、任务状态、版本、验证、Git 或发布规则。
- 必要前置：当前用户要求、`CONSTRAINTS.md`、`TASK.md` 及与本轮直接相关的代码、资料和记录。首次持久写入前按 `对话记录/Git提交备份/备份规则.md` 保存允许范围的基线。
- 输出位置：`对话记录/计划书/<任务标识>-实施计划.md`；当前任务和决策记录只保存关联路径、认可来源及必要摘要。

本文路径以项目根目录为基准；引用只是导航，按当前动作读取，不通读全部规则或历史计划。本模块不扩大已有授权和读写边界。

## 先查现状，再按缺项澄清

先自行检查代码、资料和已有决定，列出已知内容与仍需用户决定的问题。起步围绕适用主题核对已有信息，只对尚需用户决定的缺项、含糊回答或互相冲突的要求继续澄清：

- 本轮目标、现有问题、要改什么和明确不改什么；
- 用户操作顺序、希望看到的效果及受影响旧功能；
- 输入输出、界面行为和数据规则；
- 异常情况、边界、风险与回退；
- 验收方法及完成标准；
- 适用的依赖、参考资料、联网数据、费用和操作授权。

一次围绕一个主题，优先问一个关键问题，说明想确认什么及原因。回答不清时继续追问、举例或提供有依据的候选，不因已追问一次就收尾；候选与建议标为待确认，不代替用户决定。已提供或能从项目取得的信息不重复问，不要求用户回答 AI 能自行核实的技术事实。

是否结束澄清，以本轮目标、修改范围、验收标准和适用授权是否明确为依据。仍有影响本轮的关键缺项、含糊回答或互相冲突的要求时，继续追问或举例，不按已回答的问题数量提前结束；上述内容已充分明确时，用大白话复述理解并检查遗漏后即可形成计划，不为满足“多轮”凑问题。首版仍须满足立项结束、反向检查及正式需求生成或展示的前置条件。

“起步尽量问清约八成”表示主要内容应充分明确，不设固定题数或最低轮数，也不计算或宣称完成比例。可由 AI 在已确认范围内确定的普通实现细节单列，暂不影响本轮的未决事项写入任务卡，不能当作授权。

## 每轮都有计划书

每轮首版实现、功能新增、修复或优化都先保存并展示一份实施计划，简单改进可简写，但必须说明本轮改什么。纯只读答复、无关的非功能文档修正及仅按要求打包不因此另建功能计划；已提供或已认可的本轮计划按本节保存、关联后沿用，不重复生成另一轮计划或索取同一认可。

计划至少包含：

1. 本轮目的与当前问题。
2. 逐项改动清单，优先写“目前是什么 → 改完是什么效果”。
3. 修改范围、受影响部位和明确不做。
4. 实施步骤与顺序。
5. 验收方法，包括适用测试、源码预览及需人工查看的内容。
6. 风险、依赖、待决事项及可由 AI 自定的实现细节。

简单改动可按以下六项写，每项通常一两句话，复杂处按需展开，不设硬性字数上限。下面仅为占位示例，不是实际项目计划：

```markdown
# 〔任务标识〕实施计划

1. 目的与当前问题：〔本轮要解决的问题及目的〕。
2. 改动清单：〔目前是什么〕 → 〔改完是什么效果〕。
3. 修改范围：〔允许修改及受影响部位〕；明确不做：〔已确认的排除项〕。
4. 实施步骤：〔按顺序说明怎么完成本轮改动〕。
5. 验收方法：〔适用测试、源码预览、AI 审核及需人工查看的内容〕。
6. 风险与依赖：〔风险、回退及依赖〕；待决事项：〔事项及其影响〕；AI 可自定：〔已确认范围内的实现细节〕。
```

简版只缩短表达，不省略上述必要内容；计划保存、用户认可和修订留痕仍按下文执行，后续版本、备份和验证要求仍按对应模块执行。已认可计划内的普通修复和复查沿用本轮计划，不因采用简版重新申请开工。

计划描述预期，不预写功能完成、验证通过、版本已推进或提交成功。首版实施计划须在立项提问结束、反向检查及正式需求生成或展示后形成；讨论草案仍按 `规则/立项.md` 处理，不提前授权实现。

## 保存、关联与修订

每轮使用唯一且符合 Windows 文件名要求的任务标识，在 `对话记录/计划书/` 保存独立 Markdown。创建前检查目标；已有文件先读，确认属于本轮时才按本轮修订，不覆盖其他轮次或来源不明内容。保存后在回复展示计划及实际路径；无法安全保存时说明原因，不冒充已留存，不绕过未满足的计划前置开始实现。

计划正文只放计划文件；`TASK.md` 的“背景与输入”关联计划路径，并保留仍相关的正式需求与参考路径，“已确认决定”记录认可来源。按 `对话记录/记录规则.md` 在决策主记录保存计划路径、认可来源和必要摘要，其他分类只交叉引用，不复制正文。计划目录及说明随整个对话记录本地保留，不进入 Git，也不进入现有代码快照；源码和版本等文件仍按各自提交规则处理。不得在计划里抄录凭证、敏感原文或未获准引用的只读资料。

已认可的正文须保留。目标、范围或验收标准实质变化时，保留原认可内容及修订关联，展示修订内容并重新取得认可；不静默改写后假称原计划已覆盖。读取时只定位当前任务关联计划及必要变更，不通读历史目录。实际项目的预置目录或说明缺失、来源不明时，按记录结构异常规则保留现场并报告，不自动重建或覆盖。

## 认可后执行

用户明确认可本轮正式实施计划，即授权在其明确范围内进行普通实现，不再另问一次是否开工；把认可来源关联到当前任务后，按 `规则/任务执行.md` 进入实现。用户只是讨论、未答复、认可旧轮计划或认可讨论草案，均不能当成本轮正式认可。当前任务边界与唯一状态仍以 `TASK.md` 为准，长期红线仍以 `CONSTRAINTS.md` 为准，历史计划不自动成为下一轮授权。

已认可计划内可安全处理的修复、复查和重试沿用本轮计划，不反复询问，也不重复升本轮功能版本；范围外问题、授权不足或无法验证时停止相关步骤并说明。认可计划不自动授权其中未明确覆盖的删除、外部操作、费用、打包或发布；相应专项前置仍须满足。
