# 任务执行

- 何时读取：开始实施、切换任务、调整任务状态、处理需求变更或更新交接时；只读问答不触发写入。
- 职责：任务类型、任务卡、状态、换卡与日常收尾；不定义打包、发布或恢复操作。
- 必要前置：当前用户要求、`CONSTRAINTS.md`、`TASK.md`；续接再看 `handoff.md`、`对话记录/00-索引.md` 定位的相关条目。
- 输出位置：`TASK.md`、适用的 `handoff.md` 和分类记录。本文路径均以项目根目录为基准；引用仅导航，按当前动作调用，不整目录读取。

## 任务与写入权限

本模块所有持久写入动作，包括首次填写任务卡、配置调整、状态更新、换卡和交接，均先按下文的修改前基线要求保存；读取和确定范围本身不写文件。普通开发在保存基线后填写最小任务卡。快速修改仅用于明确、单点、可逆的修改，不因任务小而免除高风险确认；不得为了少填字段选择它。尚未按 `规则/立项.md` 完成提问结束和正式需求文档生成或展示时，使用“新项目立项”，不得换成普通开发或快速修改提前实现。立项完成须有需求文档或留存证据，无法确认时先澄清；其余情形或无法判断时使用普通开发。

执行者可据实更新当前任务的名称 / 标识、类型、背景与输入、风险与回退、执行进展、待决问题和满足条件的状态；可选择足以满足完成标准的验证方式，不得降低已确认验证要求。目标、允许修改、禁止修改、需再次确认和完成标准只能记录用户当场明确指令或已确认需求，逐项写入“已确认决定”及来源；不得扩张范围或放宽要求。确实不适用时填“不适用”；“无”须经当前指令、已确认需求和约束核对，不代表新增授权。

开始新任务须复核全部字段，仅带入仍影响当前任务的决定和待决问题。普通任务的任务类型、目标、允许修改、禁止修改、需再次确认、完成标准、验证方式均须为已决定值，才能变为“可执行 / 执行中”；首版及功能改进还须按 `规则/需求澄清与计划.md` 取得本轮正式实施计划认可，来源可核对，否则保持“待澄清”，只做适用的澄清与记录。快速修改最少填写类型、目标、允许修改、完成标准、验证方式、状态，其他字段只有确实不适用时可填“不适用”，现有禁止项和再次确认要求必须记录；属于功能改进时，同样不能跳过计划认可。

只读参考输入只记路径与允许 / 禁止操作，不抄内容。涉及当前实现且需要用户决定或授权的未决项先确认再实现；立项允许在已确认技术范围内自行确定的交付细节可逐项核实，不放宽要求。已确认需求不得静默改写；影响目的、功能主次、技术约束、交付或验收时先取得确认，在需求变更中写明原内容、日期、原因、来源和影响。变更使旧范围或验收失效时，不得维持“待验收 / 已完成”，按影响退回“待澄清 / 可执行 / 执行中”或换卡。

## 执行与收尾

1. 读取现状与边界，检查本轮相关代码、资料和已有证据；只读取直接相关模块及历史条目，不把未知内容当成已决定事实。
2. 本轮第一次持久写入前读取 `对话记录/Git提交备份/备份规则.md`，为允许备份的目标保存修改前基线；范围包含任务卡、配置、版本、说明、验收步骤、交接和源码，不等到修改源码才开始。执行中新增目标，先补该目标基线再写入。出现应记录事实时按 `对话记录/记录规则.md` 留痕，不等 Git 可用才记录；计划书随对话记录排除，不复制进代码快照。
3. 首版及每轮功能改进先按 `规则/需求澄清与计划.md` 多轮澄清、保存并展示本轮计划；用户已明确提供的信息不重问，已认可的同一轮计划直接沿用。任务用现有字段关联计划路径与认可来源，保留仍适用的正式需求及参考路径。未认可时只做规划和适用记录，不修改功能实现；纯只读或非功能文档任务不因此强制创建功能计划。
4. 用户认可后，在本轮明确范围内完成实现，同步有关项目文档。计划内可安全处理的问题自行更正；目标、范围或验收标准实质变化时，按计划模块保留原认可内容及变更关联，重新取得认可，不擅自扩大范围。
5. 每完成一轮功能改进，按 `规则/版本管理.md` 推进一次开发版本，同步适用的软件实际版本字段，再进入最终验证；纯文档不因此推进。功能改进或其他影响验收步骤的修改按 `规则/人工验收.md` 检查并同步相关流程。
6. 完成直接相关验证；功能改进的日常审核按 `规则/源码预览.md` 尝试源码预览，不顺带打包。整轮改进完成后、最终交付及适用提交前，按 `规则/审查方法.md` 对照认可计划和验收流程审核本轮改动与受影响旧功能；范围内可安全修复的问题自行处理，重新检查受影响部分，不改变验收标准。返工、预览失败或重试沿用本轮计划和版本，不重复升版。未完成、无法验证或需额外授权时照实报告，停止受影响步骤，继续其他可安全工作。
7. 本轮有持久改动或应追加记录事实，且使用 Git、策略为自动提交、未确认 Git 不可用时，先按 `规则/Git提交.md` 做前置核对，此步不暂存或提交；忽略规则或身份未就绪也照实处理。核验带来的文件变化同样先保存基线。随后更新本轮任务事实、实际命令、验收步骤及交接；进入待验收、暂停、完成、重要阻塞或完成高风险操作后，按实际条件更新 `handoff.md`，不承担任务状态、发布事实或未来授权。`README.md` 只同步已确认事实和命令。此时不能预写提交成功或未满足条件的任务完成；收尾改动影响验证时返回第 6 步检查受影响部分。
8. 核对最终拟提交范围，完成本轮备份清单及完整性核验，使任务、版本、说明、验收步骤和交接的实际改动均纳入允许保存的范围；缺项如实记录。只有满足适用提交条件时，才形成最终暂存证据并按 Git 提交模块提交；仅有本地记录而无可提交文件时不建空提交。已知 Git 不可用则保存本地备份和未提交状态，不反复探测、催修或加载恢复模块；用户要求修复并实际恢复后才进入 `规则/Git恢复.md`。手动或不提交按所选策略处理，不影响本地备份。
9. 核对实际提交结果，仅将提交主题、哈希及实际成功、失败或未提交状态追加到 Git 忽略的分类记录和备份索引，不回改已冻结清单。反馈实际改动、验证、失败、未完成和未验证项，提供适用的源码入口及人工查看事项，不把失败或未提交写成成功。

向用户交付时，用大白话先说结果，按本轮需要简短说明完成了哪些功能、主要改动位置和实际检查结果；区分失败、未执行及需要用户查看的事项。功能改进涉及源码预览时，给出根目录 `验证审查器` 的实际入口及必要的依赖、使用数据、隔离与关闭方式；入口未实现或不可用时说明原因及可行的下一步，预览失败按 `规则/源码预览.md` 明确提示需要重新执行。按实际情况说明开发版本、Git 提交与本地留痕状态，不把未发生的操作写成成功。简单任务只报告相关内容，不强制输出空栏目，也不默认创建交付报告文件。

最终清单形成后若拟提交内容变化，停止将旧清单及已受影响的验证结论用于新内容，补齐必要基线、相关检查并生成新的清单及完整性证据，保留旧清单的替代关联；无法取得的修改前基线按备份规则记录缺项，不补造原值。提交后确需修改受跟踪文件时，作为新的持久改动保存基线、验证、备份和按策略提交；不得声称它已包含在先前提交中。纯收尾修正不额外推进功能版本；确有新的功能改进时仍按版本规则处理。

“待验收”须完成执行者可完成的标准，并在交接中写明验证和待人工确认的限制；“已完成”须满足完成标准及必要验证、验收，未验证项只有获得明确例外并记录时才可保留。“已阻塞”须在待决问题写清对象、影响及所需条件。暂停时据实保留允许的任务状态，不新增状态值。

## 换卡与历史保留

`TASK.md` 只保留一张卡。立项完成开始实现、需求变更使旧范围或验收失效、已完成或已阻塞后开始无关任务时必须换卡；边界已超出或下一步将超出允许范围、触碰禁止项时先停止并说明，取得确认后才决定换卡，不先做后补。

1. 先据实更新旧状态，再按记录规则留存须长期保留的决定、验证、待决问题及证据，并更新索引；交接不能作为这些事实的唯一位置。正式需求已保存时只引用路径。记录库缺失或异常时保留旧卡，停止换卡并报告；待用户授权恢复或指定可长期保存的位置后继续，不自动补建、也不事后编造被覆盖事实。
2. 逐项带入仍相关的决定和待决问题，其余任务特有字段清空重填。长期边界、授权或需求决定归各自事实来源，更新须满足对应模块条件。
3. 立项转实现的新卡为“普通开发”，背景写正式需求路径。尚未保存时先按 `规则/立项.md` 的默认或用户指定位置与边界保存；无法保存时，先长期留存决定和待决事项，再把需求正文暂存于 `handoff.md` 后换卡。该正文须完整保留，直到按原定位置安全保存并更新引用，不擅自另选路径、不覆盖已有文件、不凭记忆补写。
4. 新卡边界及完成标准仍须明确来源；已获用户审核通过的讨论草案验收标准和验证方式可沿用，并记录草案的确认来源，但不替代立项结束或本轮正式实施计划认可。首版及功能改进的新卡关联对应正式计划，认可后才按成立条件进入实现；未确认的字段保持未决，新卡为“待澄清”。
5. 换卡不改变长期配置、项目初始化或发布状态，不继承旧卡授权。长期历史按记录规则分类保存；不适合脱敏摘要的附件或完整材料，仅在 README 已明确归档位置及保留方式后归档。
