# 新项目立项

- 何时读取：项目尚未完成立项、正在立项访谈，或用户明确要求重新立项时。
- 职责：访谈、框架确认、提问结束、需求输出及转交首版实施计划；不等同项目初始化，不提前授权实现。
- 必要前置：当前用户要求、`CONSTRAINTS.md`、`TASK.md` 和 `INITIATION.md` 的当前答案；任务状态或换卡按 `规则/任务执行.md`。
- 输出位置：`INITIATION.md` 立项事实、`TASK.md` 待决事项、正式需求文档及适用分类记录。本文路径均以项目根目录为基准；普通引用不触发整套规则读取。

## 访谈与记录

用户偏好把问题问充分：宁可多问几轮，不用假设填空；每个问题先说明想确认什么、为什么问。先问产品愿景的“为什么做、给谁用、希望获得什么价值”，再按答案表五节及任务边界推进，一次只推进当前章节的一个问题。使用“问题 + 2–4 个基于已确认信息的候选方向 + 我自己填”；没有可靠上下文时只保留“我自己填”。存在关键缺项、含糊回答或互相冲突的要求时，继续追问、举例或核对，不以追问一次为上限；必要建议明确标为“待确认”，不视为已确认。已提供的信息直接归入章节，只补问缺项，不要求用户回答 AI 能自行核实的技术事实。是否结束澄清，以目标、修改范围、验收标准和适用授权是否明确及下文立项结束条件为准；充分明确时进入反向审查及正式需求流程，不为满足“多轮”凑问题，也不因达到某个问题数就收尾。“约八成”表示主要内容充分明确，不是固定题数、轮数或可计算的完成比例；可由 AI 自定的普通实现细节单列。

执行者将已确认答案和当前章节据实写入 `INITIATION.md`，未决事项集中写入 `TASK.md`，按记录规则保存脱敏历史，不重复初始化骨架。关键技术选择、外部依赖或架构取舍须写选定项与理由。任务边界和授权只在 TASK 与 CONSTRAINTS，不在需求正文另建一套；实质变更须确认，不能以记录答案为由扩张授权。

确认根目录 `验证审查器` 双击源码入口和交付形态；Windows EXE 只在用户明确要求打包验证时生成。主 EXE、启动器实现、打包命令、健康检查和依赖可在获得相应实现授权后，于已确认技术范围内确定；交付要求、关键技术选择、约束或授权的实质选择仍问用户。每次回复末尾简述已确认、未决和下一步。

## 提问结束与反向审查

“提问结束”前只可提问、记录已确认内容、展示候选、给待确认建议或讨论计划书草案；不得输出最终实现计划、把假设当定案、编码或开始实现。进入收尾前反向检查明确不做、可判断的验收、关键依赖、风险和回退是否遗漏。

以下大框架均确认后，才可把答案表当前章节改为“提问结束”，并明确告诉用户“立项提问结束”：

- 产品愿景、项目目的；至少一项功能写明优先级、使用场景、验收标准。
- 明确不做至少一项；用户明确确认“无额外明确不做事项”也可，执行者不得自行填“无”或借此放宽约束。
- 交付形态、可双击的源码审核入口；Windows EXE 另完成 CONSTRAINTS 的 EXE 产物策略。
- 整体验收要求，以及 TASK 的允许修改、禁止修改、需再次确认。

其他待填写、待确认或未知项可保留，但必须逐项列入 TASK 待决问题，不当作授权；涉及当前实现且需用户决定的项须先确认。功能范围和验收要求明确后，在允许范围按 `规则/人工验收.md` 建立具体项目流程，操作随实现逐步补齐，不冒称尚未实现或核实的步骤通过，也不因此提前实现。

## 草案与正式需求

大框架确认后可在“提问结束”前给计划书草案讨论；必须含“我的假设”和“待你确认”，假设不写进验收标准，其他未定项列待决问题。草案是讨论稿，审核通过不等于提问结束或实现授权；正式需求是首版实施计划的依据，不能以草案认可代替正式实施计划认可。

提问结束后按下方格式生成正式需求，保留已确认愿景、五节内容及验收，未确认项标“待确认”并同步 TASK。默认保存根目录 `需求文档.md`，用户指定其他位置时从其指定。先核对目标与写入边界：目标不存在且允许才保存，必要项目内目录可按任务范围创建；已有、只读或可写性不明时不覆盖、不另选路径，先展示正文并在 TASK 记录阻塞或待决事项。

正式需求已生成或展示且反向审查完成后，按 `规则/需求澄清与计划.md` 保存并展示首版实施计划，写清首版改动和验收范围。用户认可正式实施计划即授权按其明确范围开工，不再重复询问；尚未认可时可以继续讨论、修订和记录，不开始实现。认可后按任务执行模块结束立项并换“普通开发”卡，未保存需求时按换卡规则先留存，并关联需求及认可计划路径。立项完成不改变 CONSTRAINTS 的初始化状态，初始化只在需要时按 `规则/初始化.md` 独立判断，可发生在访谈任一阶段。

