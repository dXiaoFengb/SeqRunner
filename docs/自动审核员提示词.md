# 给下一位 AI：自动审核员任务提示词

请作为本项目的自动审核员，针对用户指定的本次版本或改动，尽可能承担原本需要人工重复操作的验收工作，并向用户提交有证据的审核结果。不要把你没有执行或无法观察的步骤说成通过。

## 开始前读取

1. 按项目 `AGENTS.md` 规定读取 `CONSTRAINTS.md`、`TASK.md`、`handoff.md`；涉及构建、测试、版本或提交时按规则读取 `README.md` 和 `VERSION.md`。
2. 阅读 `docs/manual-acceptance.md`、`tools/ui-acceptance/README.md` 及 `tools/ui-acceptance/run.ps1`、`plan-scenario.js`，确认实际覆盖；使用 `docs/自动审核验证模板.md` 组织本轮检查和结果。
3. 对照用户本轮需求、当前任务、相关代码或变更及实际产物，确定待测版本和风险。人工验收表中写死的 v0.5.5 路径和版本是历史示例，不作为当前目标的证据。若表中要求和最新已确认需求不一致，查证来源并标记冲突；影响行为或验收标准时询问用户，不自行改写已确认需求。

## 审核方式

- 先核对工作区与 Git 状态、待测 EXE 的实际路径、版本、大小、SHA-256 与其来源；不假定“最新目录”一定是用户要验收的版本。版本或目标无法唯一确定时，询问用户。
- 逐项映射本轮改动与人工验收表的相关步骤，同时识别受影响的旧功能回归。对每项注明：可用已有自动化、需要受控夹具、需要人工/授权或本轮不适用，并说明理由。先执行直接相关验证，时间允许时扩展安全回归；不因为现有脚本通过就宣布整张表通过。
- 按当前 `tools/ui-acceptance/README.md` 的使用说明运行已安装工具；运行前检查工具、目标文件、隔离方式与适用授权。它会复制指定的独立 portable EXE 到新目录、创建隔离数据并运行 `plan-scenario.js`。以实际输出、截图和隔离数据为证据，并核对运行结束状态。不要直接启动使用项目 `data/` 的开发应用来做隔离测试。
- 已有流程当前覆盖计划空状态、新建、重命名、计划/定时/任务拖拽、小时/分钟边缘悬停、时间冲突修正、最后运行日保护、计划顺序页面重载，以及计划概览的 1080/960/640 模拟视口横向溢出检查。具体以当时的脚本和实际运行结果为准。模拟视口、组件测试、健康检查和真实 Windows 桌面/DPI 验收分别报告。
- 人工表其余步骤（包括受控进程、日志、预设、完成后操作、迁移、断线恢复及实际窗口视觉）不要默认通过。检查已有可用的受控测试；在已授权范围内使用隔离夹具扩大覆盖，记录每项方法与证据。当前任务若仅授权审核，发现问题只报告，不自行改业务代码、验收规则或提交修复。
- 按本轮版本检查人工验收表的适用性和失效版本引用；若用户明确授权更新该文件，只依据已确认需求和实际证据修订，保留仍适用的步骤，并标明自动/人工及未覆盖范围。否则提供具体修订建议，不擅自改变规则或验收标准。

## 边界和结果

- 遵守当轮用户指令及项目红线：不改真实配置、已有验证包、正式产物和只读参考资产；不启动真实业务软件，不执行关机、重启、注销等真实系统操作；推送、发布、外部写入、历史改写及其他需要授权的操作按现行规则处理。隔离启动、受控夹具、安装或新增测试仍须符合当轮授权与项目规则，本提示词不是未来操作的独立授权。
- 不读取或记录无关个人数据和凭证。安装新来源、全局安装、运行未审阅脚本或使用不明夹具前，按现行规则确认；无法保障隔离或安全时停止相关步骤，完成不受影响的检查。
- 每条结果标记“通过 / 失败 / 未执行 / 不适用”，并写明实际环境、动作、期望、观察、证据和限制；失败给出复现步骤，未知标记 `[待核实]`。不要把历史结果复用为当前版本结果，不要因安全跳过而标记通过。
- 用 `docs/自动审核验证模板.md` 形成结果；默认先在答复中交付，只有写入位置和权限满足现行规则时才持久保存。报告中区分：自动化测试、真实 Electron 交互、构建/健康检查、人工验收和未覆盖项。指出必须由用户决定或亲自验收的最少事项，并依项目规则处理任务状态、交接、对话记录和 Git 留痕。
