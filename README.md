# 项目启动说明

这是顺序任务调度器 V2 的开发目录，继承原项目 v0.17.1 源码与 Git 历史。规则模块按动作读取；真实业务、外部通知、EXE 打包和发布遵守当前项目授权边界。

## 文件怎么分工

| 位置 | 负责内容 |
| --- | --- |
| `AGENTS.md` | 简短底线、权威顺序和按动作读取入口 |
| `CONSTRAINTS.md` | 长期选择、红线、只读资产及精确授权 |
| `TASK.md` | 当前任务、边界、待决问题和唯一任务状态 |
| `INITIATION.md` | 立项访谈答案与提问进度 |
| `VERSION.md` | 开发版本、打包台账、正式版本与发布历史 |
| `handoff.md` | 当前交接周期的改动、证据与下一步快照 |
| `规则/` | 各项操作的方法与成立条件；具体入口只在 `AGENTS.md` 导航 |
| `对话记录/` | 本地分类历史、索引、每轮计划书和备份，不进入 Git |
| 本文件 | 项目概况、实际命令、目录说明及用户指引 |

保留核心文件及全部规则模块；不适用配置填“无 / 不适用”，不删除文件制造悬空引用。记录区、交叉引用区、最新条目空位和备份索引无项目事实时保持空白。

本目录仍作为空白模板维护时，不执行复制后项目的初始化、任务留痕、升版、提交、备份或打包流程，不把模板维护填成项目进度。

## 怎么使用

下表是操作摘要，具体规则仍从 `AGENTS.md` 按动作调用，不因查看表格而读取全部模块。

| 场景 | 必要步骤摘要 | 需要用户回答或认可的位置 |
| --- | --- | --- |
| 只读审查 | 读取相关现状与规则，反馈意见；不写项目文件、记录或备份，不运行软件 | 审查范围不明时补充说明 |
| 首次立项 | 立项与初始化分别判断；保存允许范围的基线后记录答案，按缺项澄清，再反向检查、生成或展示正式需求、保存并展示首版计划，认可后进入实现 | 决定关键目标、范围、交付、验收及授权；认可首版正式计划 |
| 简单功能改进 | 核对现状与边界，补齐关键缺项，保存并展示简版计划，认可后走下述完整流程 | 有关键缺项时回答；认可本轮计划，实质变更或额外授权另行确认 |
| 普通功能改进 | 核对现状与边界，按缺项澄清，按复杂度保存并展示计划，认可后走下述完整流程 | 确认关键需求、范围及验收；认可本轮计划，实质变更或额外授权另行确认 |
| 仅打包验证 | 核对当前版本与范围，使用独立目录打包，检查实际验证包全部适用功能及最终文件，记录并交付；失败按既有清理规则处理 | 明确提出打包要求；必要信息或授权不足、检查无法执行时决定后续处理 |
| 正式发布 | 核对指定版本、产品及证据，满足发布条件后执行并记录实际结果 | 明确要求发布，确认发布版本、指定产品、目标及发布动作 |

功能改进的完整流程：修改前基线 → 澄清、保存并展示计划及取得认可 → 实现 → 一轮功能完成后推进开发版本并同步适用的软件实际版本 → 相关测试、源码预览和 AI 审核 → 更新收尾文件 → 最终备份 → 按条件提交 Git 并追加实际结果 → 反馈源码入口及人工查看事项。任务卡、配置等文件也须在首次持久写入前保存允许范围的基线。

简单与普通功能改进遵守相同要求，区别只在计划和说明的详略，不新增任务模式或豁免。已认可计划内的普通修复和复查沿用本轮计划，不重复申请开工或推进本轮版本。日常不打包；仅执行打包或发布、不含功能改动时，不额外创建功能改进计划。

同类事实只在负责文件维护，其余位置引用；普通链接不表示要求立即读取。继续项目时先看任务、交接和历史索引，按相关记录 ID 定位，不必从头读完历史。

每轮计划保存在 `对话记录/计划书/<任务标识>-实施计划.md`，正文在回复中展示；决策记录保存路径和认可来源，当前任务关联本轮计划。整个目录本地保留，不进入 Git 或现有代码快照。澄清、计划内容、认可及修订细则只由 `规则/需求澄清与计划.md` 负责，按本次动作读取。模板仅预置计划目录说明，不填真实计划或项目事实。

## 用户资料怎么放

- `只读资料/`：放参考材料和原始输入。原文件默认只读；明确要求借用内容时，可在任务内复制到可编辑位置修改副本，原件不动。具体边界以 `CONSTRAINTS.md` 为准。
- `资源/`：放图片、素材等可用资源；能否使用、修改或纳入 Git，根据来源和用途确认。
- 测试夹具、临时输出、生成结果另外说明位置，不与原始资料混放。已有文件不自动移动，来源不明先确认。上述建议目录仅在实际需要且允许时创建。

`对话记录/` 固定本地保存；备份按内容哈希去重，说明和数据都随本项目保管，仅考虑同项目保存。

## 日常入口与产物位置

根目录 `验证审查器` 供双击查看当前源码的软件内容，扩展名按项目确定；实际依赖、数据隔离和关闭方式由项目说明与人工验收流程提供。

Windows EXE 项目仅在明确要求时打包：工作位置 `产物/工作/<开发版本>/<尝试标识>/`，验证位置 `产物/验证/<开发版本>-<尝试标识>/`，发布位置 `产物/发布/<版本>/`。每次打包使用独立目录。已交付验证包由用户自行使用，AI 日常不管理旧包；失败清理和正式发布各走对应模块。

## 项目档案

- 项目名称 / 定位：顺序任务调度器；Windows 本地桌面程序，按用户配置的顺序执行软件任务，并通过计划、日志与运行历史管理执行。
- 技术栈：Python 3.13、FastAPI、Pydantic、Uvicorn、Vue 3、TypeScript、Vite、Electron。
- 目录结构（源 / 测试 / 产物 / 发布）：`backend/`、`frontend/`、`electron/` 分别为后端、前端和桌面主进程，测试与源码相邻；`scripts/`、`tools/` 为开发和验收工具。`data/`、`node_modules/`、`backend/.venv/` 和 `产物/工作/`、`产物/验证/`、`产物/发布/` 不进入 Git。
- 构建命令：`npm run build` 构建前端。旧 EXE 打包入口因依赖未迁移的历史验证包并与 V2 规则不一致，现已暂停；需在未来获得明确打包授权后按新规则重建和验证。
- 测试命令：`backend\.venv\Scripts\python.exe -m pytest backend/tests`、`backend\.venv\Scripts\python.exe -m ruff check backend`、`npm run typecheck`、`npm run test:frontend`、`node --test electron/*.test.cjs`、`npm run validate:audit-coverage`。最后一项仅核查测试文件映射，不执行测试或代表验收。
- 发布路径与动作：见 `VERSION.md`
- Git 与记录策略：见 `CONSTRAINTS.md`

本文件的已确认项目事实、实际命令和失效引用可据实更新，不得借此改变规则；涉及规则含义时先按治理修改模块处理。

## 源码预览与依赖

在 Windows 安装 Python 3.13 和 Node.js 后，运行 `py -3.13 -m venv backend\.venv`、`backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt` 和 `npm ci`。依赖安装受当前项目的来源和脚本授权约束。双击 `验证审查器.cmd`，入口会选择动态本机端口并为每次启动创建新的隔离临时数据目录；关闭程序窗口即可退出。该预览不会使用项目原有 `data/`，不会打包；每次启动的数据互不继承。

旧 `tools/feature-preview/` 和 `tools/ui-acceptance/` 包含迁移参考脚本；旧的历史证据门禁和旧打包命令不作为 V2 的验证或发布入口。项目人工验收方法见 `人工验收流程.md`。
